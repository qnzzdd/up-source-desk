# UP 源台 MVP v1 · 范围与实现约定

> 状态：草案（待确认后提交）
> 适用版本：首版，单用户、本机运行
> 关联文档：`README.md`、`docs/PLAN.md`

---

## 1. 首版要解决的问题

把"关注了 3000 个人"变成"每天知道我在意的那些人发了什么、值不值得看"。

首版不做视频内容的全量读取。成本结构决定了这一点：

- 拉**元数据**是每天几千次的量级，可以承受；
- 逐条读**视频内容**（下载、转写、全文分析）是每天几万次且不可预期的量级，不可承受。

因此首版的核心手段是：**标题 + 可选的热评 + 动态正文与图片分类**，用它们在低成本下推断"这条内容大概是什么"。

## 2. 核心模型：分组即策略，未分组即不采集

### 2.1 同步与采集是两件事

| 动作 | 范围 | 频率 | 说明 |
| --- | --- | --- | --- |
| 关注列表同步 | 全部关注（可 3000+） | 每日 1 次 | 只负责**发现**：新增、改名、取关 |
| 内容采集 | **仅已分组且分组启用**的 source | 由分组策略决定 | 唯一的成本来源 |

同步只更新"谁存在"，不触发任何内容请求。因此不存在"新关注自动开始拉取"的情况。

### 2.2 新加入的 UP 一律进入「未分组」

- 同步发现的**新增关注**落入 `未分组` 状态；
- `未分组` 不等于 `暂停`：`暂停` 是你主动关掉的，`未分组` 是尚未被纳入监控；
- 未分组状态下**不发起任何内容采集**，只保留：mid、昵称、头像、关注时间；
- Web 端显示「本次新增 N 个未分组 UP」，由你决定归入哪个分组；
- 归组这个动作本身即视为"开始监控"，不需要额外的开关。

### 2.3 分组在设置时确认

- 归组入口：未分组列表、UP 详情页、批量选择；
- 归组时必须选择**一个已有分组**或**新建分组**，不接受"先归组、后设策略"的空转状态；
- 策略挂在分组上，UP 归组即继承分组策略；
- 单个 UP 可设置 `override`，覆盖所属分组的任意字段（用于"这个 UP 我要盯紧一点"）。

## 3. 分组策略字段

策略是分组对象的属性，字段如下：

| 字段 | 取值 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `frequency` | 15m / 1h / 6h / 24h / 手动 | `24h` | 轮询间隔 |
| `depth` | `L0` / `L1` / `L2` / `L3` | `L1` | 采集深度，见 §4 |
| `comment_mode` | `off` / `top10` / `top20` | `off` | 评论采样条数 |
| `comment_trigger` | `always` / `views_gt_N` / `title_match` | `views_gt_10000` | 满足条件才拉评论 |
| `image_mode` | `off` / `classify` / `download` / `analyze` | `classify` | 图片档位，见 §5 |
| `analyze_daily_cap` | 0–10，整数 | **`1`** | 每个 UP 每天最多几张图进入 AI 分析，用户可调 |
| `inference` | `none` / `title` / `title_comment` / `with_image` | `title` | 交给模型的信息量 |
| `max_requests_per_cycle` | 整数 | `200` | 单周期请求上限 |
| `max_tokens_per_cycle` | 整数 | `100000` | 单周期 token 上限 |
| `fail_threshold` | 1–10 | **`3`** | 连续失败达到该次数即标黄并自动暂停 |
| `state` | `active` / `paused` | `active` | 暂停即完全不采集 |

**频率与深度正交**：高频浅采（1h + L0，只要标题）和低频深采（24h + L2）是两种合法组合，不是同一根刻度上的两点。

---

## 4. 采集深度定义

| 档位 | 拉取内容 | 请求量（每 UP 每周期） | 适用 |
| --- | --- | --- | --- |
| `L0` | 最新投稿的 bvid、标题、发布时间 | 1 | "只要知道发了没" |
| `L1` | L0 + 封面 URL、时长、播放、简介前 100 字 | 1 | 默认档，能支撑标题推断 |
| `L2` | L1 + 满足 `comment_trigger` 的视频拉热评 top10/20 | 1 + N | 需要判断"值不值得看" |
| `L3` | L2 + 按 `image_mode` 处理图片 | 1 + N + M | 图文动态为主的 UP |

`L1` 与 `L0` 的请求次数相同，差别只在响应字段的使用范围——**默认给 `L1`，因为它几乎不增加成本**。

## 5. 图片处理四档

设计原则：**分类先于下载，下载先于分析**。绝大多数图片不值得花 token。

| 档位 | 行为 | 成本 | 输出 |
| --- | --- | --- | --- |
| `off` | 仅保存图片 URL | 0 | 无 |
| `classify` | 拉**缩略图**做轻量分类 | 极低（几百字节/张） | 类别标签 + 置信度 |
| `download` | 下载原图到本地 | 带宽 + 磁盘 | 本地文件 |
| `analyze` | OCR + 一句话画面描述（多模态） | 800–1500 token/张 | 文本摘要 |

### 5.1 分类标签

`截图` / `图表` / `长图` / `照片` / `插画` / `表情包` / `封面` / `无法判断`

分类依据（按优先级）：宽高比、尺寸、缩略图视觉特征、来源上下文（视频封面 / 动态配图）。

### 5.2 按类别决定是否升级

| 类别 | 默认去向 | 理由 |
| --- | --- | --- |
| 截图、图表、长图 | 升级到 `analyze` | 图片本身就是信息载体 |
| 照片、插画 | 停在 `classify` | 描述价值低，token 浪费 |
| 表情包 | 停在 `classify`，不下载 | 无信息量 |
| 封面 | 一律不分析 | 封面是点击诱饵，不是内容 |
| 无法判断 | 停在 `classify` | 不赌 |

### 5.3 限额

- 每 UP 每天进入 `analyze` 的图片数不超过 `analyze_daily_cap`，**默认 1 张**，用户可在 0–10 之间调整；
- 超出限额的图片降级为 `classify`，不排队、不留悬案；
- 单周期图片总量超 `max_requests_per_cycle` 时排队至下一周期，UI 显示队列长度，不静默丢弃。

## 6. 内容推断卡

### 6.1 输出结构

```json
{
  "target_type": "video",
  "subject_tags": ["编程", "开源"],
  "possible_content": "某开源项目的部署实测",
  "evidence": ["标题含「实测」", "热评提到「踩坑」「Docker」"],
  "information_sufficiency": "medium",
  "worth_reading": "如果你需要该项目的部署经验",
  "confidence": 0.6,
  "model": "…",
  "prompt_version": "v1",
  "input_hash": "…"
}
```

### 6.2 三条硬规则

1. **置信度上限由信息量决定**：仅标题 → 上限 0.5；标题 + 热评 → 上限 0.7；再加图片 → 上限 0.85。
2. **措辞随置信度变化**：低置信度用「标题显示…」，不得写成「视频讲了…」。
3. **信息不足就输出 `information_sufficiency: low` 并给出空内容**，不允许补全或推测具体情节。

### 6.3 评论预处理

- 只取按点赞排序的前 10 / 20 条；
- 丢弃：纯表情、少于 6 字、重复刷屏、明显的引战与人身攻击；
- 评论作者昵称、头像、mid **不入库、不发送给模型**。

## 7. 数据模型（在 PLAN 基础上调整）

新表：

| 表 | 关键字段 |
| --- | --- |
| `video_meta` | bvid（唯一）、source_id、标题、封面 URL、时长、pubdate、播放、简介摘要、首次发现时间 |
| `comment_sample` | video_id、采样条数、采样时间、过滤规则版本 |
| `inference` | target_type、target_id、`input_hash`、模型、提示词版本、置信度、输出 JSON、生成时间 |
| `dynamic_post` | dynamic_id、source_id、类型（原创/转发/视频卡）、正文、图片数、pubdate |
| `media_asset` | 图片哈希、所属对象、分类标签、分类置信度、是否已下载、是否已分析 |
| `image_analysis` | media_asset_id、OCR 文本、描述、模型、成本记录 |
| `source_policy_override` | source_id、被覆盖的字段及取值 |

调整：

- `source` 增加 `monitor_state`（`ungrouped` / `grouped` / `paused`），与 `paused` 语义分开；
- `sync_cursor` 必须区分三种结果：**接口返回空**、**游标失效**、**请求失败**；
- `content.platform_status`：正常 / 已删除 / 仅粉丝可见 / 地区限制。

`inference.input_hash` 是必需的：标题或热评变化时必须能重算，否则缓存会长期返回旧结论。

## 8. 失败处理

- 单 source 连续失败达到 `fail_threshold`（**默认 3 次**，用户可调 1–10）→ 标黄并置为 `paused`，需人工恢复；
- 恢复动作由你在 UI 上点一次，不做自动重试复活；
- 失败原因必须分类记录：网络 / 鉴权失效 / 限流 / 风控验证 / 接口结构变化；
- **失败不得进入"无更新"统计**。

## 9. 日报与覆盖率

日报顶部固定显示：

```
本期覆盖：3 个分组 / 57 个监控对象
采集失败：3（已标黄）
暂停中：2
未分组（未监控）：1240
```

三条约束：

1. 覆盖率 ≠ 关注总数，必须分开显示"未监控"；
2. 部分失败的日报标注 `partial`，不伪装为完整；
3. 同日期日报幂等，重复生成覆盖旧文件并保留生成记录。

## 10. 验收标准

| 项 | 标准 |
| --- | --- |
| 关注同步 | 3000 关注一次同步成功率 ≥ 99%，耗时 ≤ 10 分钟 |
| 采集准确性 | 选中 100 个 UP，连续 3 个周期无重复内容入库 |
| 推断质量 | 人工抽检 20 条，`information_sufficiency: high` 的条目中，描述与内容不符 ≤ 1 条 |
| 成本可控 | 单周期请求数与 token 数均不超过分组设定上限 |
| 失败可见 | 人为断网 1 个周期，对应 source 被正确标黄，日报标 `partial` |
| 未分组隔离 | 新增关注后，未归组的 UP 产生 0 次内容请求 |

## 11. 明确不做

- 视频下载、ASR 转写、逐条全文分析
- 字幕抓取（可得率低，留待 v2 评估）
- 自动取关或任何写操作
- 多用户、云端账号、公开分享、移动端
- 人脸识别、人物身份推断
- 转发动态的图片分析
